## システム概要

### アプリケーション名
**Alphaus MSP Revenue Simulator (compare-risp)**

### 目的
AWS Managed Service Provider (MSP) 向けに、保険型Reserved Instance/Savings Plan（保険RI/SP）と標準RI/SPのコスト最適化を行うシミュレーションツール。複数のAWSリソースの組み合わせで最適な購入戦略を提案し、損益分岐点を可視化する。

### 主要機能
1. **コスト最適化シミュレーション**: 保険RI/SP（30日保証/1年保証）と標準RI/SP（1年/3年契約）のコスト比較
2. **動的リソース選択**: 18種類以上のAWSサービス（EC2, RDS, ElastiCache等）とインスタンスタイプの組み合わせ
3. **返金見込み計算**: カバレッジが100%未満の場合、未使用分の保険料を返金見込みとして算出
4. **可視化**: 累積コスト推移グラフ、月次コスト比較、詳細テーブル
5. **マイクロフロントエンド対応**: スタンドアロン、iframe埋め込み、single-spa統合をサポート

## 技術選定の理由

### フロントエンド

#### Next.js 15 (App Router)
**選定理由:**
- **SSR/SSGのハイブリッド**: 初期ロードの高速化とSEO最適化を両立
- **API Routes**: 別途バックエンドサーバーを立てることなく、サーバーレスAPIを構築可能
- **ファイルベースルーティング**: 直感的なディレクトリ構造でメンテナンス性が高い
- **AWS Amplifyとの親和性**: ゼロコンフィグでのデプロイが可能

**トレードオフ:**
- ❌ Next.js固有の学習コストが必要
- ✅ 長期的にはメンテナンス性とパフォーマンスで利益が上回る

#### React 19
**選定理由:**
- **Actions & Optimistic Updates**: フォーム送信とUIの即座の更新を簡潔に実装
- **コンポーネント再利用性**: UI部品の高い再利用性と保守性
- **大規模なエコシステム**: Chart.jsなどのライブラリとの豊富な統合

**トレードオフ:**
- ❌ 最新版のため一部ライブラリの互換性に注意が必要
- ✅ 最新機能による開発効率の向上

#### TypeScript 5.6
**選定理由:**
- **型安全性**: コンパイル時のエラー検出により、実行時バグを大幅に削減
- **IDEサポート**: 自動補完とリファクタリング支援により開発効率が向上
- **複雑な計算ロジックの明確化**: 保険料・割引率・返金見込みなどの複雑な計算ロジックを型で明確化

**トレードオフ:**
- ❌ 初期開発の型定義作業が必要
- ✅ バグ削減とメンテナンス性で長期的に大きな利益

#### TailwindCSS 3.4
**選定理由:**
- **ユーティリティファーストアプローチ**: 迅速なUI開発とデザインの一貫性
- **カスタマイズ性**: Alphaus独自のブランドカラー（Blue系、緑系）を容易に適用
- **バンドルサイズの最適化**: 未使用のCSSを自動削除（PurgeCSS内蔵）

**トレードオフ:**
- ❌ HTMLクラスが多くなり可読性が下がる場合がある
- ✅ 保守性とパフォーマンスで大きなメリット

#### React Chart.js 2
**選定理由:**
- **豊富なチャートタイプ**: 累積コストグラフ、月次コスト比較に対応
- **レスポンシブ**: 自動的にコンテナサイズに適応
- **カスタマイズ性**: 損益分岐点の注釈、色の変更などが容易

**トレードオフ:**
- ❌ 複雑なカスタマイズは学習コストが高い
- ✅ 標準的なチャート機能には十分

### バックエンド

#### Next.js API Routes (Lambda@Edge)
**選定理由:**
- **サーバーレス**: インフラ管理不要で自動スケーリング
- **コードの一元管理**: フロントエンドとバックエンドを同一リポジトリで管理
- **TypeScript共有**: 型定義をフロントエンドとバックエンドで共有可能
- **低レイテンシ**: CDNエッジでの実行により、グローバルに低レイテンシ

**トレードオフ:**
- ❌ 複雑なバックエンドロジックには不向き（実行時間制限あり）
- ✅ 本アプリのシンプルな計算ロジックには最適

### デプロイメント

#### AWS Amplify Hosting
**選定理由:**
- **フルマネージド CI/CD**: Gitプッシュで自動ビルド・デプロイ
- **グローバルCDN**: CloudFrontによる高速配信
- **環境変数管理**: デプロイ環境ごとの設定を容易に管理
- **プレビュー環境**: プルリクエストごとに自動でプレビュー環境を生成

**トレードオフ:**
- ❌ AWS特化のため、他クラウドへの移行が困難
- ✅ AWS環境での運用コストとメンテナンス性が最適

## データフローの概要

### ユースケース 1: シミュレーション実行

```
1. ユーザー操作: リソース選択 & 設定入力
   │
   ├─► [ResourceSelector Component]
   │   ├─ サービス選択（EC2, RDS, etc.）
   │   ├─ インスタンスタイプ選択
   │   └─ 数量入力
   │
   └─► [SimulationConfig Component]
       ├─ 保険プラン選択（30日保証/1年保証）
       ├─ 標準プラン選択（1年/3年、支払方法）
       ├─ カバレッジ設定（0-100%）
       └─ 使用率設定（0-100%）

2. データ送信: フロントエンド → API
   │
   POST /api/simulate
   {
     "insurance": "30d",
     "standard_term": "1y",
     "standard_option": "no_upfront",
     "coverage": 0.8,
     "usage": 0.8,
     "resources": [
       { "service": "EC2", "instance": "c5.2xlarge", "quantity": 10 }
     ]
   }

3. サーバー側処理: API Route (route.ts)
   │
   ├─► pricing-catalog.ts から価格データ取得
   │   └─ 18種類以上のAWSリソース価格情報
   │
   ├─► simulator.ts でコア計算実行
   │   ├─ 保険RI/SP計算（割引率、保険料、返金見込み）
    │   ├─ 標準RI/SP計算（初期費用、月額コスト）
    │   │   └─ 利用率適用: RIはAllUpfrontのみ、NoUpfront/PartialUpfrontとSPは100%稼働として課金
   │   ├─ 累積コスト計算（12ヶ月分）
   │   └─ 損益分岐点算出
   │
   └─► レスポンス生成
       {
         "baseline_cost": 7944.0,
         "insurance": { ... },
         "standard": { ... },
         "cumulative": { ... },
         "details": [ ... ]
       }

4. データ表示: フロントエンド
   │
   ├─► [SimulationResults Component]
   │   ├─ CostCards: 月額コスト、削減額、ROI
   │   ├─ CumulativeChart: 累積コスト推移グラフ
   │   ├─ MonthlyChart: 月次コスト比較
   │   └─ DetailsTable: リソース別詳細
   │
   └─► [DiscountRateInfo Modal]
       └─ 割引率、保険料率、実効割引率の詳細
```

### ユースケース 2: PostMessage API（iframe統合）

```
1. 親アプリケーション → compare-risp
   │
   window.postMessage({
     type: 'UPDATE_CONFIG',
     insurance: '1y',
     coverage: 0.9
   }, 'https://compare-risp.your-domain.com')

2. compare-risp内での処理
   │
   ├─► window.addEventListener('message', handleMessage)
   │   ├─ オリジン検証（セキュリティ）
   │   ├─ メッセージタイプ判定
   │   └─ 状態更新
   │
   └─► 自動的にシミュレーション再実行

3. compare-risp → 親アプリケーション
   │
   window.parent.postMessage({
     type: 'SIMULATION_COMPLETED',
     result: { ... }
   }, parentOrigin)
```

### データの流れの特徴

- **リアクティブ**: React Stateによる自動再レンダリング
- **非同期**: API呼び出しは非同期で、ローディング状態を表示
- **エラーハンドリング**: APIエラー時はユーザーフレンドリーなメッセージを表示
- **型安全**: TypeScriptによる型チェックでデータ整合性を保証

## 非機能要件の考慮事項

### 1. パフォーマンス

#### 目標
- **初期ロード時間**: 3秒以内（First Contentful Paint）
- **API応答時間**: 500ms以内
- **インタラクション応答**: 100ms以内

#### 実装戦略

**SSG（Static Site Generation）の活用**
- 静的ページ（Header, Footer, 初期UI）は事前生成
- CDNキャッシュにより高速配信

**コード分割**
```javascript
// 遅延ロードコンポーネント
const CumulativeChart = dynamic(() => import('./CumulativeChart'), {
  loading: () => <Skeleton />
})
```

**バンドル最適化**
- TailwindCSS PurgeCSS: 未使用CSSの削除
- Next.js自動最適化: Tree shaking、Code splitting

**計算ロジックの最適化**
- `simulator.ts`内の計算は時間計算量 O(n) （nはリソース数）
- 最大100リソースまで対応可能（実用上は10〜20リソース）

### 2. セキュリティ

#### 脅威モデル

| 脅威 | 対策 |
|-----|-----|
| XSS（クロスサイトスクリプティング） | Reactの自動エスケープ、`dangerouslySetInnerHTML`の不使用 |
| CSRF（クロスサイトリクエストフォージェリ） | Next.jsのSameSite Cookie（デフォルト） |
| PostMessage乗っ取り | オリジン検証（allowedOrigins配列） |
| 入力値検証 | TypeScript型チェック + API側でのバリデーション |

#### 実装例: PostMessage オリジン検証

```typescript
const allowedOrigins = [
  'https://wave.onedev.alphaus.cloud',
  'http://localhost:3000'
]

const handleMessage = (event: MessageEvent) => {
  const isLocalhost = event.origin.startsWith('http://localhost:')
  const isAllowed = allowedOrigins.includes(event.origin) || 
                    (process.env.NODE_ENV === 'development' && isLocalhost)
  
  if (!isAllowed) {
    console.warn('[compare-risp] Unknown origin:', event.origin)
    return
  }
  // 処理続行...
}
```

## アーキテクチャ上の重要な設計判断

### 1. モノリシックNext.jsアプリケーション vs マイクロサービス

**選択: モノリシックNext.jsアプリケーション**

**理由:**
- ✅ シンプルな計算ロジックで、マイクロサービス化するメリットが小さい
- ✅ デプロイが単純（単一リポジトリ、単一ビルド）
- ✅ フロントエンドとバックエンドで型定義を共有可能
- ❌ 将来的に複雑化した場合は、マイクロサービス化を検討

### 2. クライアント側計算 vs サーバー側計算

**選択: サーバー側計算（API Routes）**

**理由:**
- ✅ **計算ロジックの保護**: コア計算ロジック（保険料算出など）をクライアント側に露出しない
- ✅ **データ整合性**: 価格カタログをサーバー側で一元管理
- ✅ **将来の拡張性**: データベース連携、履歴保存などが容易
- ❌ ネットワークレイテンシが発生（対策: API応答時間を500ms以内に最適化）

### 3. REST API vs GraphQL

**選択: REST API**

**理由:**
- ✅ シンプルなエンドポイント（3つのみ: `/simulate`, `/pricing`, `/resources`）
- ✅ Next.js API Routesとの親和性が高い
- ✅ GraphQLのオーバーヘッドが不要
- ❌ 将来的に複雑なクエリが必要になった場合はGraphQLを検討

### 4. インメモリ価格カタログ vs データベース

**選択: インメモリ価格カタログ（pricing-catalog.ts）**

**理由:**
- ✅ 価格データの変更頻度が低い（月1回程度）
- ✅ データサイズが小さい（18種類のリソース）
- ✅ 高速アクセス（DB接続不要）
- ✅ デプロイが簡単（環境構築不要）
- ❌ 将来的に価格データが大規模化した場合はDBを検討

### 5. 累積コスト計算のフロントエンド実装 vs バックエンド実装

**選択: バックエンド実装（simulator.ts）**

**理由:**
- ✅ 計算ロジックの一貫性（全ての計算をサーバー側で実行）
- ✅ クライアント側のバンドルサイズ削減
- ✅ 計算ミスのリスク低減（単一責任の原則）
